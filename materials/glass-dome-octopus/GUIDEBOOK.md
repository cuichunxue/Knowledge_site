# 再現ガイドブック：参考画像1枚から「分解できる3Dロボット」を作る

Glass-Dome Octopus の制作（STEP 1〜4）を、別の題材でも同じ手順で再現できるようにまとめた手引きです。
各 STEP で実際に使ったプロンプトの要点、コマンド、数値、つまずいた点と直し方を、作業の順に並べています。

- 完成品：`materials/glass-dome-octopus/index.html`
- 参考技術：[Nyxera0x/cutaway](https://github.com/Nyxera0x/cutaway)（MIT）
- 所要時間の目安：STEP 2〜4 は、それぞれ Claude Code の 1 セッション分（数時間）

---

## 0. 全体像

| STEP | やること | 成果物 | 止まるところ |
|---|---|---|---|
| 1 | 参考画像を作る | `assets/reference.png` | — |
| 2 | 画像を計測し、Three.js のコードだけで 3D を組む（静止画ループ 2 ラウンド） | 3D モデル・CHECKLIST・JOB_DESCRIPTION | 人間の承認 |
| 3 | 参考と 3D の差を数値で測り、2 ラウンド改善 | QUALITY_REPORT・比較画像 | 人間の承認 |
| 4 | 部品単位の分解・全体分解・再組み立て・カメラ演出・UI | 分解アプリ・STEP4_TEST_REPORT | 人間の承認 |
| 5 | 動画（未着手） | — | — |

方式の核心は次の 3 つです。

1. **プロンプトではなく仕事の説明書**：`JOB_DESCRIPTION.md`（全制作に共通のルール）と `CHECKLIST.md`（その画像専用の合格条件）を渡し、毎回読ませる。
2. **目で見て判断せず、数値で測る**：比率・色の割合・暗い部分の割合・位置の誤差をスクリプトで測る。
3. **2 ラウンドごとに止まる**：人間が承認するまで次の STEP に進ませない。

### three.js をリポジトリに同梱する

CDN に頼らず、必要なファイルだけを `vendor/` に置きます。

```sh
mkdir -p vendor/three/addons
cp package/build/three.module.js package/build/three.core.js vendor/three/
cp package/examples/jsm/controls/OrbitControls.js \
   package/examples/jsm/geometries/RoundedBoxGeometry.js \
   package/examples/jsm/utils/BufferGeometryUtils.js vendor/three/addons/
cp package/LICENSE vendor/three/
```

```html
<script type="importmap">
{"imports":{"three":"./vendor/three/three.module.js","three/addons/":"./vendor/three/addons/"}}
</script>
```

ローカル確認は `python3 -m http.server 8000` で行います。ES Modules を使うため、`file://` では動きません。

## 2. STEP 1：参考画像

ChatGPT に投げるプロンプト（[ ] を題材に差し替える）：

```
A robotic [octopus] as a precision machine, studio product shot on a near-white background with a soft floor shadow.
White glossy shells with clearcoat, green only on tips, rims, edges and joint rings.
Dense dark mechanism showing through cut-outs and clear glass: gears, pistons, hoses, small screws.
Eyes as glossy black lenses with a thin green ring.
Front three-quarter view, the whole animal in frame.
```

題材の選び方：

- 関節が多く、中に機構が詰まっているものを選ぶ。表面がつるっとしたもの（蛇・貝）は避ける。
- 主な肢は 1 種類だけにする（足・羽・触手のどれか）。
- インフォグラフィック（説明図つき）の画像でもよい。その場合は「中央の大きな本体を基準にし、分解図は内部構造の補助資料にする」と指示する。

## 3. STEP 2：計測 → チェックリスト → 静止画ループ

### 3-1. 指示の要点（実際のプロンプトの骨子）

```
役割：Three.js / プロシージャルモデリング / ロボット機構に詳しい 3D エンジニア。
添付の参考画像を忠実に再現し、ブラウザで 360° 観察できる 3D を作る。cutaway の設計と実装を調べ、使えるものは再利用する。
コーディングの前に：比率・色の面積比・肢の本数と関節数・視点・光源を数値化し、10〜12 行のチェックリストを作る。
必須：スマホ/PC 対応、回転・ズーム・リセット、自動回転、部品名表示、GitHub Pages で動く。
禁止：球と円柱だけのおもちゃ、画像を板に貼る、テストしていない機能を完成と書く、未測定の FPS を達成と書く。
2 ラウンド比較・修正したら、スクリーンショットと HTML を提示して止まる。
```

### 3-2. 計測（コードを書く前）

背景を除いた本体の画素について、色の面積比を測るスクリプトを用意します（`tools/measure.py`）。

| 分類 | 条件 |
|---|---|
| 背景 | 輝度 > 222 かつ 彩度 < 0.06 |
| 暗部 | 輝度 < 80 |
| 緑 | G > R + 35 かつ G > B − 10 |
| 白 | 輝度 > 175 かつ 彩度 < 0.12 |

Glass-Dome Octopus の参考画像は、暗部 0.285 / 緑 0.089 / 白 0.322 でした。比率（本体の高さ / 幅、ドーム径、肢の付け根と先端の太さ、肢の長さ）は、画像上の画素で読み取ります。

### 3-3. CHECKLIST.md の書き方

- 10〜12 行。シルエット → 一番の特徴 → 材質 → アクセント色 → 密度、の順に書く。
- あいまいな言葉には数値を付ける（「太い」→「付け根の直径は本体幅の 0.20」）。
- 陥りやすい既定の失敗には **NEVER** を書く（「NEVER 滑らかな 1 本のチューブ」）。
- 最後の行は必ず「暗部の割合が参考の 0.8 倍以上」。

### 3-4. 作り方の要点

| 部分 | 作り方 |
|---|---|
| 形状 | cutaway の `sweepX`（断面を回転させてリング・ドーム・装甲板を作る）、`gearGeo`（歯車）、`tube`（配線）を流用 |
| 肢 | Object3D の**親子階層**（root → joint0 → joint1 …）にし、各関節のローカル Transform を保存する。描画は部品の種類ごとに 1 つの **InstancedMesh** にまとめ、関節のワールド行列をインスタンスに写す（後で分解するため） |
| 肢の節 | 節の長さを半径に比例させ、二分探索で「ちょうど n 節」になる歩幅を求める。向きは平行移動フレームで決め、装甲がねじれないようにする |
| 材質 | 白はクリアコート、暗い金属は環境反射を弱める（envMapIntensity 0.3〜0.5）。ガラスは transmission。発光は emissive と toneMapped: false |
| 照明 | ソフトボックスの環境マップ（PMREM）＋キー・リム・フィル。床は ShadowMaterial（影だけを描く）＋放射グラデーションの接地影 |
| 画質 | 指が触れる端末・小さい画面は低画質ティア（透過なし・影 1024・画素比 ≤ 1.5）。FPS が低いと画素比を下げ、さらに透過を切る |

### 3-5. 静止画ループ

1. 参考と同じ構図で 1600×900 の静止画を撮る（Playwright、`?shot=hero&ui=0`）。
2. 参考と並べ、チェックリストの全行を YES / PARTIAL / NO で採点する。記憶ではなく画像と比べる。
3. NO → PARTIAL の順に直す。
4. **2 ラウンドで止めて**、人間に見せる。
5. 失敗は「数値付きで 1 行」JOB_DESCRIPTION の修正ログに足す。

## 4. STEP 3：差を数値で測って直す

### 4-1. 指示の要点

```
参考と 3D の差を定性的・定量的に分析して直す。「似ている」とだけ評価するのは禁止。
参考の中央を切り出し、同じ角度・距離・画角でレンダリング。正面・側面・背面・斜め 45° も保存。
12 項目を重み付き（15/15/10/10/10/10/5/5/5/5/5/5%）で 0〜100 点採点。内部指標であり画像類似度ではないと明記。
形状比率・色の比率・暗部密度（参考の 80% 以上）・機械構造の数を測る。
P0（構造の不一致）→ P1（質感不足）→ P2（細部）の順。最大 2 ラウンド。悪化した変更は原因を調べて直すか戻す。
```

### 4-2. 計測を公平にする工夫

| 対象 | 方法 |
|---|---|
| 参考画像 | 50px の格子を重ねた拡大画像から手で読む（輪郭 ±5px、肢の長さは折れ線で ±10%） |
| 3D の形状 | モデル自身の寸法をカメラで画面に投影して計算する（`src/measure.js`）。全体の幅と高さは、黒一色のシルエット描画（`scene.overrideMaterial`）の外接矩形 |
| 3D の色 | シルエットのマスクで本体の画素だけを正確に切り抜く。背景のしきい値で除く方式は使わない |
| 採点 | 計測から機械的に出す部分と、目視の判定部分を分けて `tools/score.py` に固定する。後から再計算・監査できる |

### 4-3. Glass-Dome Octopus の結果（参考）

| 指標 | 改善前 | ラウンド 2 |
|---|---|---|
| ドームの見える高さ / 本体径 | −20.9% | −4.7% |
| カメラの径 | +34.2% | +8.7% |
| 肢の配置（参考と一致） | 5 / 8 | 8 / 8 |
| 緑の割合 | 0.74 倍 | 0.86 倍 |
| 重み付きスコア | 70.0 | 79.0（目標 85 に未達） |

STEP 2 の読み取りの誤り（ガラスは半球ではなく球の上 61%、肢は「上 2・横 2・手前 4」で奥向きなし）は、格子を重ねて読み直して初めて分かりました。**STEP 3 では参考画像を必ず格子付きで読み直す**こと。

## 5. STEP 4：分解・再組み立て

### 5-1. 指示の要点

```
STEP 3 の外観を維持したまま、部品単位の分解・全体分解・逆再生の再組み立て・分解スライダー・クリック選択と強調・
選択部品へのカメラ移動・説明表示・360° 回転・スマホ対応・安全な復元を実装する。ランダムに飛ばす演出は禁止。
部品グループ（P01 ドーム … P07〜P14 肢 1〜8、P15 パッド）。肢は根元のロック解除 → 分離 → 関節が段階的に開く。
render(p) は保存した初期 Transform から毎回絶対位置を計算する（加算しない）。同じ p なら同じ配置。
テスト：連続 20 回、スライダー 100 回、途中で部品変更、画面回転、WebGL エラー、FPS・メモリ。未実施は未実施と書く。
```

### 5-2. 設計の型（そのまま流用できる）

**(1) 状態だけで描画が決まる（`explosion.js`）**

```js
state = {p, ind}                        // p: 全体の分解率、ind[id]: 部品ごとの分解率
e[id] = max(stage(p, 区間開始, 区間終了), ind[id])
e.P01 = max(e.P01, e.P02, e.P05)        // 依存：コアやギアの前にドームが上がる
render(state):
  for (各オブジェクト) 初期 Transform に戻す   // 加算しない
  部品ごとに e から位置・回転を計算して置く
```

- 最初の 17% をロック解除（ボルトが浮く・レンズが回る・ロックリングが回る）、残りを分離にする。
- 回転は Quaternion。各部品のイージングは render の中に置き、アニメーション側は線形にする。

**(2) アニメーションは状態を動かすだけ（`animation.js`）**

- トゥイーンは常に**現在値から**始める。途中で逆再生しても、部品を変えても跳ばない。
- 時間は `performance.now()` × 速度。テストでは 8 倍速にする。

**(3) 肢の分解**

- 根元を外れる方向へスライドする。関節 i のローカル位置に `(隙間, 0, 0)` を足し、親の節の軸に沿って開く。根元から順に開く。
- 開いた隙間には、長さを隙間に合わせて伸ばした軸とピストン（InstancedMesh）を出す。
- パッドは「カップ・リム・吸引口」を別のレイヤーにし、それぞれ自分の法線方向に違う距離だけ浮かせる。

**(4) カメラ（`cameraDirector.js`）**

- 注視点は、部品を開いた状態を一度仮に描いて目印の位置を読み、すぐ元の状態を描き直して求める。描画が状態だけで決まるからできる方法。
- 位置と注視点を両方補間する。ユーザーがドラッグしたら、すぐに自動の動きを捨てる。

**(5) 選択（`interaction.js`）**

- レイキャストで部品を拾う。InstancedMesh はインスタンス番号から関節と肢を割り出す。
- 強調は法線方向に押し出した緑の輪郭（裏面だけを描く）。`MeshBasicMaterial` では `objectNormal` が使えないので、頂点属性の `normal` を使う。
- 周りの部品は半透明にする（マテリアルを差し替え、元に戻せるよう保持）。肢を選んだときは、他の肢をインスタンスの色で暗くする。

### 5-3. 衝突（貫通）を設計で避ける

`tools/collide.mjs` で、分解率を 0〜1 の 41 段階に分けて走らせます。組み立て状態では離れていたのに途中で重なる組み合わせを「新しい接触」として数え、部品名で確認してから直します。

実際に見つかって直したもの：

| 衝突 | 直し方 |
|---|---|
| 側面の大きな板が、同じ方位の肢に向かって開く | 板は主に上へ動かす |
| ギアが、持ち上がった肢の高さで横へ抜ける | ドームが空けた上の空間へ抜く |
| カメラの光軸がやや下向きで、真下の肢に当たる | 最初の引き出しを「外＋上」にする |
| 肢のすぐ横の板 | その肢が外れるまで 25% だけ動かす |

円盤状の部品は外接箱の角が実物より大きく、誤検出になります。結果は「候補」として扱います。

## 6. テストの作り方（GPU なし環境で安定させる）

| 落とし穴 | 対策 |
|---|---|
| ソフトウェア描画は 1fps 前後で、固定の待ち時間では間に合わない | `waitForFunction` で「条件が満たされるまで待つ」 |
| 1 フレームの撮影に十数秒かかる | `screenshot({timeout: 180000})` |
| 画面中央を白くする CSS の重ね表示が、黒を灰色に持ち上げていた（暗部 0.067 と誤計測） | canvas の上に**明るくする**重ね表示を置かない。計測は UI を消して撮る |
| ダブルタップで部品まで開いた（シングルタップの選択とダブルタップのリセットを別々に判定していた競合） | 判定を 1 か所にまとめる |
| 重いフレームでタップの間隔が伸びる | `event.timeStamp` で時刻を測る。保留タイマーが発火したときに次のタップが進行中なら、その指離れまで判定を待つ |
| CDP のタッチは前の処理が終わるまで次が送られない | `Input.dispatchTouchEvent` に `timestamp` を明示する |
| FPS が実機と違う | ソフトウェア描画の値は「記録のみ」とし、**目標達成とは書かない** |

用意したテスト：

- `tools/test_step4.mjs`（25 項目）：15 部品の選択、肢を 1 本ずつ、全体分解・再組み立て（初期位置との誤差 0）、スライダー、途中での逆再生、一時停止、ドラッグとアニメーションの競合、クリック選択、連続 20 回、ランダム 100 回、決定論、途中での部品変更、メモリ、スマホ（タップ・折りたたみメニュー・回転・ピンチ・画面回転）
- `tools/test.mjs`（24 項目）：STEP 2・3 の操作の回帰テスト

外観の維持は、STEP 3 と同じ条件で撮った画像との画素差で確かめます（Glass-Dome Octopus は 0.012%）。

## 7. ドキュメントの残し方

| ファイル | 中身 |
|---|---|
| `JOB_DESCRIPTION.md` | 共通ルール＋修正ログ。**1 行 1 件、数値付き**。次の題材で同じ失敗をしないための資産 |
| `CHECKLIST.md` | 計測値・チェックリスト・再計測・部品の設計表（接続先・ロック解除・動き・依存・区間） |
| `QUALITY_REPORT.md` | 計測方法・実測値・改善前後・採点の内訳・未解決の問題 |
| `STEP4_TEST_REPORT.md` | テストごとの結果と記録値、未実施・未検証、未解決の課題 |
| `quality/*.json` | 生データ（報告書の数値はここから） |

報告のルール：

- 存在しない画像や測定値を書かない。
- 実機で確認していないことは「エミュレーションの範囲」と書く。
- 目標に届かなかったら、届かなかったと書く。

## 8. 次の題材に流用するときのチェックリスト

- [ ] 参考画像を 50px の格子付きで読み、比率・配置・色の割合を CHECKLIST に書いた
- [ ] 肢は親子階層＋InstancedMesh で組み、関節のローカル Transform を保存した
- [ ] 計測はモデルの投影とシルエットのマスクで行い、UI を消して撮った
- [ ] 2 ラウンドごとに止めて承認を取った
- [ ] 分解は `render(state)` の純関数で、初期 Transform から絶対値で計算している

- [ ] 衝突チェックの候補を部品名で確かめて、軌道を直した
- [ ] テストは条件待ちで書き、往復 20 回・ランダム 100 回で誤差 0 を確認した
- [ ] FPS・実機は「未検証」と正直に書いた
- [ ] 失敗を数値付きで JOB_DESCRIPTION に 1 行ずつ足した
